# Attack Report: T1021.001 — Remote Desktop Protocol Lateral Movement

**Date:** 2026-11-10  
**ATT&CK ID:** T1021.001  
**Technique:** Remote Services — Remote Desktop Protocol  
**Tactic:** Lateral Movement  
**Tool:** xfreerdp (open-source FreeRDP client)  
**Attacker:** Kali Linux — 192.168.2.40 (ATTACKNET segment)  
**Targets:** Windows Server 2022 Domain Controller — 192.168.1.10
(labnet segment) and Windows 10 Evaluation — 192.168.1.30 (labnet
segment)  
**Credential used:** Domain Administrator plaintext password,
`AdminLab@2026`, extracted from LSASS memory in Attack 4 (T1003.001)  
**Detection result:** FULL on Windows 10 (no configuration changes
required) — network-layer BLOCK on the Domain Controller (segmentation
control working as designed)  
**Ground truth timestamp:** Logged via `gtruth`, see
scenario-001.csv  

---

## Technique Description

T1021.001 represents the moment stolen credentials become operational.
Credential dumping (T1003.001) produces data — hashes, tickets, or
plaintext passwords sitting in a dump file. Lateral movement is what
proves that data is dangerous: using it to open a genuine, interactive
session on another machine in the environment. This report documents
both outcomes observed when testing this technique against two
different targets in the same domain, using the same stolen
credential.

This attack directly follows the chain established in prior Phase 3
reports: T1110 established an initial foothold pattern via brute
force, T1059.001 demonstrated PowerShell-based execution, and
T1003.001 extracted the domain Administrator's plaintext password
(`AdminLab@2026`) from live LSASS memory. T1021.001 is the next
logical step any real attacker would take with that credential.

## Target 1 — Domain Controller (192.168.1.10): Network-Layer Block

### Pre-attack reachability test

Before attempting any credential use, basic network reachability was
tested per the established verification discipline of this lab:

```bash
gtruth "T1021.001" "test RDP reachability to DC 192.168.1.10 before lateral movement attempt - expect block per pfsense rule 4"
ping -c 2 192.168.1.10
nmap -p 3389 192.168.1.10
```

```
ping 192.168.1.10
--- 192.168.1.10 ping statistics ---
2 packets transmitted, 0 received, 100% packet loss

nmap -p 3389 192.168.1.10
Note: Host seems down. If it is really up, but blocking our ping
probes, try -Pn
```

### Confirming the block type

Nmap's own suggestion was followed to distinguish "host down" from
"host filtered":

```bash
nmap -Pn -p 3389 192.168.1.10
```

```
Host is up.
PORT     STATE    SERVICE
3389/tcp filtered ms-wbt-server
```

"Filtered" is Nmap's terminology for a port where a SYN probe received
no response of any kind — neither a SYN-ACK (open) nor a RST (closed).
This is the specific signature of a silent firewall drop, consistent
with pfSense's `Block` action (as opposed to `Reject`, which would
return a TCP RST). Combined with the earlier 100% ICMP packet loss,
this confirms pfSense Rule 4 on the ATTACKNET interface — which
explicitly blocks all traffic from Kali (192.168.2.40) to the Domain
Controller (192.168.1.10) — is functioning exactly as designed,
silently dropping every packet type without exception.

### Result

**T1021.001 against the Domain Controller never reached the
authentication stage.** The stolen domain Administrator credential,
however valid, was never evaluated by Windows, because the network
transport itself was severed before any RDP negotiation could begin.
This is a positive security control finding, not a detection gap — the
architecture decision made during network segmentation (see
troubleshooting-log/006) directly prevented lateral movement to the
most sensitive machine in the domain, independent of credential
strength.

## Target 2 — Windows 10 (192.168.1.30): Successful Lateral Movement

### Reachability confirmed

```bash
nmap -Pn -p 3389 192.168.1.30
```

```
3389/tcp open  ms-wbt-server
```

pfSense ATTACKNET Rule 2 (Kali to Windows 10, any port) permits this
path, in direct contrast to the DC result above.

### Connection attempt

```bash
gtruth "T1021.001" "RDP lateral movement to 192.168.1.30 using stolen domain admin credential AdminLab@2026"
xfreerdp /v:192.168.1.30 /u:Administrator /d:homelab.lab /p:'AdminLab@2026' /cert:ignore
```

**Flag reference:**

| Flag | Meaning |
|---|---|
| `/v:192.168.1.30` | Target IP address |
| `/u:Administrator` | Username |
| `/d:homelab.lab` | Domain — required to authenticate as the domain account rather than a local Windows 10 account of the same name |
| `/p:'...'` | Password |
| `/cert:ignore` | Skip certificate validation prompt (self-signed lab certificate) |

### Client-side observations

The xfreerdp client log surfaced several noteworthy warnings during
connection:

```
[WARN] Using /p is insecure
[WARN] Passing credentials or secrets via command line might expose
       these in the process list
[WARN][com.freerdp.crypto] [DANGER] Certificate not checked,
       /cert:ignore in use
[WARN][com.freerdp.crypto] [DANGER] This prevents MITM attacks from
       being detected!
[ERROR][com.winpr.sspi.Kerberos] Cannot find KDC for realm
        "HOMELAB.LAB"
```

The Kerberos failure is significant: xfreerdp first attempted modern
Kerberos authentication, which requires contacting the Domain
Controller's Key Distribution Center (KDC). This failed — most likely
because Kali cannot reach the DC for this purpose, consistent with the
network segmentation demonstrated against Target 1. Rather than
aborting, xfreerdp automatically degraded to NTLM authentication and
the connection succeeded regardless. This fallback behaviour is an
important and specific finding: network controls that block the
"proper" modern authentication path do not necessarily stop an
attacker whose tooling can gracefully fall back to an older protocol.

### Connection succeeded

A full interactive graphical Windows 10 desktop session opened,
authenticated as the domain Administrator. This is a complete,
unambiguous lateral movement success.

## Forensic Reconstruction from Windows Security Event Log

Two related logon events were recorded on Windows 10, 2 seconds apart,
corresponding precisely to the Kerberos-failure-then-NTLM-fallback
behaviour observed on the client side.

### Event 1 — 09:23:08 — Network pre-authentication (Logon Type 3)

```
Event ID:    4624
Logon Type:  3 (Network)
New Logon:   Administrator (HOMELAB)
Workstation Name:       kali
Source Network Address: 192.168.2.40
Logon Process:          NtLmSsp
Authentication Package: NTLM
Package Name (NTLM):    NTLM V2
Key Length:             128
```

Windows recorded the source workstation's self-reported hostname —
"kali" — verbatim. This is sent by the RDP client during the TLS/NLA
handshake and logged by Windows, making it a direct forensic indicator
of the client tool's origin.

### Event 2 — 09:23:10 — Full interactive session (Logon Type 10)

```
Event ID:    4624
Logon Type:  10 (RemoteInteractive)
Restricted Admin Mode: No
Elevated Token:         Yes
New Logon:   Administrator (HOMELAB)
Workstation Name:       WINDOWS10DESKTO
Source Network Address: 192.168.2.40
Logon Process:          User32
Authentication Package: Negotiate
Logon GUID:  {faab6b46-c342-77bc-db39-91be15ec7c96}
```

This is the authoritative record of the successful lateral movement:
a RemoteInteractive (full desktop) session, carrying an Elevated
Token, sourced from the ATTACKNET segment.

### Significance of the two-event pattern

The sequence — Logon Type 3 (NTLM network pre-auth) immediately
followed by Logon Type 10 (RemoteInteractive, Negotiate) — is the
well-documented forensic signature of a standard RDP connection. An
analyst or detection rule that only watches for Logon Type 10 would
still catch the final result, but understanding the Type 3 precursor
provides a roughly 2-second earlier warning opportunity in a real
incident timeline — a meaningful margin when automated response
actions (account lockout, session termination) are in play.

## SIEM Detection Analysis

<!-- Note: Wazuh dashboard screenshot available if captured; results summarised below from direct query -->

Two Wazuh rules fired on this event, in sequence, with **no
configuration changes required** — unlike T1059.001 and T1003.001,
this technique was fully covered by Wazuh's default ruleset from the
outset.

| Timestamp (UTC) | Rule ID | Description | Level |
|---|---|---|---|
| 09:23:10.199 | 92657 | Successful Remote Logon Detected - User:\Administrator - NTLM authentication, possible pass-the-hash attack - Possible RDP connection. Verify that kali is allowed to perform RDP connections | 6 |
| 09:23:12.267 | 92653 | User: HOMELAB\Administrator logged using Remote Desktop Connection (RDP) from ip:192.168.2.40 | 3 |

### Rule analysis

**Rule 92657** is the same rule that fired during the T1110 brute
force attack in Attack 2 — Wazuh recognises the generic NTLM
authentication pattern independent of how the credential was obtained
(brute-forced vs stolen). Notably, the alert text itself names the
source workstation directly — *"Verify that kali is allowed to perform
RDP connections"* — because xfreerdp's self-reported hostname ("kali")
was captured in the raw event data and surfaced into the human-readable
alert. This is an unusually actionable default rule.

**Rule 92653** is a dedicated RDP-specific logon detector, distinct
from the generic NTLM pattern match. It states plainly, in full
sentence form, exactly what occurred: user, domain, protocol, and
source IP. Having both a generic (92657) and protocol-specific (92653)
rule fire on the same event provides corroborating, defense-in-depth
detection — a real analyst would see two independent confirmations of
the same lateral movement event.

## Detection Verdict

**FULL on Windows 10** — both relevant Wazuh rules fired immediately
on first attempt with zero configuration changes, a contrast worth
noting against the multi-layer pipeline fixes required for T1059.001
and T1003.001.

**BLOCKED at the network layer on the Domain Controller** — the
segmentation control (pfSense ATTACKNET Rule 4) prevented the
technique from ever reaching the authentication stage, independent of
credential validity. This stands as a positive, working security
control rather than a detection gap.

## Lessons Learned

**Stolen credentials are only as dangerous as the network paths
available to them.** The domain Administrator password extracted in
Attack 4 is objectively the most powerful single piece of data in this
entire lab — yet it accomplished nothing against the Domain Controller,
purely because of where the attacker was positioned on the network.
This is the practical, demonstrated value of network segmentation as a
control independent of credential hygiene, detection coverage, or any
other layer.

**Authentication protocol fallback is a double-edged consideration.**
Kerberos failing and NTLM succeeding meant the "more secure" modern
protocol path was blocked, yet the attack still succeeded via
automatic degradation. A mature security posture would monitor for and
potentially alert on NTLM usage specifically where Kerberos should be
available and expected, since its presence can itself indicate either
a configuration problem or an attempt to route around a security
control.

**Default SIEM coverage varies significantly by technique.** This
report's finding — full detection with zero configuration changes
needed — stands in deliberate contrast to the multi-hour investigations
required for T1059.001 (Incident 007) and T1003.001 (Incident 008).
Not every technique requires a custom rule; documenting what already
works correctly is as valuable to a Phase 4 rule-writing effort as
documenting what doesn't, since it tells you where engineering effort
is and isn't needed.

**Alert text quality matters.** Rule 92657's specific mention of the
source workstation name by value ("kali") rather than a generic
placeholder demonstrates how well-designed detection rules can surface
genuinely actionable, specific information directly in the alert
summary, reducing the investigation burden on a SOC analyst compared
to a rule that only states "suspicious logon detected."

## SA Market Relevance

This technique and its outcome directly illustrate why Joint Standard
2 (FSCA/PA, effective June 2025) and similar frameworks mandate network
segmentation as a distinct control alongside credential management and
detection capability for South African financial institutions. A
compromised credential with full-domain reach is a materially worse
incident than the same credential confined to a single workstation by
network architecture — this report provides concrete, measured evidence
of that difference using a real, working domain Administrator
credential against two different network positions in the same
environment.
